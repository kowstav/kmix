# Native confirmation protocol frozen 9 October 2026

Development evidence: research_round14_native_wave_analysis_v1.json. All four
arms remain in the finite confirmation set: three dimensionally different
resource trades and the tiny output-precision gain. This is not a claim that
any is a production winner. Do not optimize them using confirmation outcomes.

Each arm gets eight pre-existing canonical confirmation regions, split across
two four-worker commits: A = 8,10,12,14; B = 9,11,13,15. Each region comprises
2 MiB matched warmup and 1 MiB scored continuation; both full 3 MiB archives
independently reconstruct. No selected word or easy-bit-only evaluation.

The signed effect is baseline minus candidate: actual archive bytes, warm coded
Q16 ideal bytes, encode/decode user+system CPU, and paired per-run peak RSS.
Archive gains must not be summed with model/code savings more than their actual
deployment multiplicity. Report individual clusters, sums and min/max. Eight
confirmation clusters do not satisfy the ten-cluster bootstrap contract.

Each region alternates execution order as in the registered development module.
Use the same binary hashes and immutable input assets. Neutral archive AND Q16
hashes must agree with the earlier native confirmation reference, despite
different machines. If they do not, stop attribution and diagnose portability.

Compare Pareto vectors, not a made-up CPU-to-bit exchange rate. A compute arm may
remain useful with a small bit penalty, but do not call it a compression gain.
Cross-host absolute speed is not used to price an arm; only its matched host
baseline is. Positive aggregate timing with contradictory regional signs calls
for an A/B/B/A timing repeat on the same host before deployment claims.

No interaction is inferred from single-arm savings. Separately preflight and
screen guard × match-pruning on development before confirmation, using the same
input bytes and actual final-coder feedback. Never reuse its development as an
untouched confirmation. Other combinations require distinct recorded hypotheses.

Five concurrent private CPU commit slots are the observed limit. Submit A first;
submit B only into slots released normally by completed jobs. Do not duplicate
accepted jobs, bypass quotas or alter the usageLimited Goal. Every job keeps four
independent pinned processes and a 10.3-hour deadline. No GPU or paid rental.
